# 성능 예산

주요 ERP 화면의 번들 증가를 배포 전에 감지한다. `npm run build`가 완료되면 `postbuild`가 다음 항목을 자동 검사한다.

- 대시보드 초기 JavaScript: 185,000바이트 이하
- 전체 거래내역 초기 JavaScript: 175,000바이트 이하
- 통합 결재함 초기 JavaScript: 205,000바이트 이하
- 재무 업무 홈 초기 JavaScript: 115,000바이트 이하
- 지출결의 초기 JavaScript: 330,000바이트 이하
- 가장 큰 지연 로딩 청크: 98,000바이트 이하
- 지출결의 지연 로딩 JavaScript 합계: 175,000바이트 이하

초기 JavaScript는 페이지와 공통 최상위 레이아웃의 청크를 중복 없이 합산한다. 즐겨찾기 편집 화면은 편집 버튼을 누를 때만 불러온다. 이 지연 로딩 화면을 위해 비동기 합계 예산에 9,000바이트를 추가했으며 당시 초기 로딩 기준은 유지했다.

직접 확인할 때는 먼저 `npm run build`를 실행하거나, 기존 `.next` 결과가 있다면 `npm run performance:check`를 실행한다. 예산을 초과하면 빌드가 실패하므로 Vercel 운영 배포도 중단된다.

일시적인 확인이 필요하면 아래 환경변수로 기준을 바꿀 수 있지만, 운영 기준 변경은 번들 증가 원인을 검토한 뒤 `scripts/check-performance-budget.mjs`의 기본값과 이 문서를 함께 수정한다.

- `EXPENSE_RESOLUTION_INITIAL_JS_BUDGET`
- `EXPENSE_RESOLUTION_ASYNC_CHUNK_BUDGET`
- `EXPENSE_RESOLUTION_ASYNC_TOTAL_BUDGET`


기간별 결재권한 기능에서는 입사일·권한 시작일 및 문서 기준일 스냅샷을 처리하는 초기 코드가 381,577 → 384,494바이트로 약 2.9KB 증가했다. 원문 결재일·확인 근거 입력으로 작성 화면 청크가 94,160 → 96,777바이트로 약 2.6KB 증가했다. 최대 비동기 청크 기준은 98,000바이트를 유지한다.

## 지출결의 초기 조회 경량화

2026-11-15 리팩토링에서는 일반 목록 진입 시 작성 전용 데이터(결재문서, 지출정책, 미연결 은행·카드 거래, 운영비 세부항목)와 다음 결의서 번호를 조회하지 않는다. 해당 데이터는 작성·수정 시 한 번만 병렬 조회한다. 목록의 자식 자료 조회도 결재 계정과 통합업무 연결만 유지하고, 항목·계정배분·증빙 원본은 상세를 열 때 선택한 문서 한 건에 대해서만 조회한다.

프로덕션 빌드 기준 초기 JavaScript는 385,789바이트, 최대 지연 청크는 96,777바이트, 지연 청크 합계는 115,024바이트였다. 이 변경의 주된 효과는 초기 서버 쿼리와 RSC 직렬화 데이터 감소였다.

## 상세·출력 지연 로딩과 전사 경로 예산

2026-11-15 성능 개선에서는 상세 작업영역과 A4 출력 미리보기를 실제 동적 청크로 분리했다. 지출결의 초기 JavaScript는 385,789바이트에서 327,826바이트로 57,963바이트(약 15.0%) 감소했다. 상세·출력 기능이 지연 청크로 이동하면서 비동기 합계는 173,477바이트가 되었고, 초기 진입 개선을 되돌리지 않도록 지출결의 초기 예산을 330,000바이트로 낮췄다.

같은 검사에서 대시보드, 전체 거래내역, 통합 결재함, 재무 업무 홈도 각각 현재 기준에 작은 여유만 둔 경로별 초기 JavaScript 예산으로 검증한다. 출력·상세 기능은 사용자가 열 때만 내려받으므로 비동기 합계 증가는 의도된 분리 결과이며, 최대 단일 지연 청크 98,000바이트 제한은 그대로 유지한다.
