## 연결 모델과 중복 방지

`vouchers`와 `voucher_lines`는 그대로 사용하고 조직별 회계 관리 메타데이터, 원본 연결, 변경 이력만 추가한다. 표의 이름은 신규 제안이다.

| 추가 구조 | 역할 / 제약 |
| --- | --- |
| `workflow_voucher_links` | 조직, 전표 ID, 사건 종류, 사건 ID, 목적, 원본 스냅샷/버전. 일반 원본 ID는 TEXT, 지급/배분 등 UUID는 명시적 FK로 검증한다. 사건 종류와 ID만 받아 임의 조직의 원본 연결 금지. |
| `workflow_voucher_controls` | 전표별 관리 상태, lock_version, 작성·검토·확정 사용자/시각, 수정 사유, 원본 지문, 원전표 ID. 기존 approval_status와 RPC 내에서 일관되게 갱신한다. |
| `workflow_voucher_events` 또는 기존 `workflow_events` | 명령별 전후 스냅샷, 담당자 ID, 사유, 시간. 확정 분개·원본 링크는 변경 불가. |
| 기존 `workflow_operations` | 조직+operation_key 유일, 명령/입력/사용자 일치 시 결과 재사용. `ACCOUNTING:` 이름공간. 같은 키로 다른 금액/계정 입력은 실패. |

업무 중복키와 재시도 키는 별개다. 새 UUID를 발급해도 같은 사건 전표를 다시 만들 수 없어야 한다.

| 목적 | 최초 전표 업무 중복키 | 연결 방식 |
| --- | --- | --- |
| 거래 발생 인식 | 조직 + 공통 거래 ID + `RECOGNITION` | 1건의 총액을 최초 인식. 원본 버전은 스냅샷이며 중복키에 포함하지 않는다. 원본 변경 시 새 버전의 같은 비용을 중복 생성하지 않고 정정 흐름으로 보낸다. |
| 실제 지급/회수 | 조직 + 실제 지급 ID + `PAYMENT` | 지급 1건당 최초 전표 1건. 각 배분 ID/금액과 원거래 ID를 연결해 분할지급과 묶음지급을 모두 추적한다. 회수는 별도 IN 지급 ID를 사용한다. |
| 계좌 이체 | 조직 + 이체 ID + `TRANSFER` | 출금/입금 두 원본을 한 사건으로 연결. 비용·신규 납부 0. 은행 전표 헤더의 단일 FK만으로 양쪽 관계를 표현하지 않는다. |
| 확정분 역분개 | 조직 + 원전표 ID + `REVERSAL` | 원분개 차·대변 교환한 전표 1건. 중복 역분개 금지. 원전표를 삭제하거나 은행 ID를 신규 역분개 헤더에 복사하지 않는다. |
| 정정 대체전표 | 조직 + 정정 사건 ID + `REPLACEMENT` | 원전표/역분개와 같은 정정 묶음으로 연결. 최초 사건의 유일키를 해제하지 않는다. 연속 정정은 현재 유효 대체전표에서 새 정정 사건으로 시작한다. |
| 수기 | 조직 + 수기 사건 ID + `MANUAL` | 사유 및 실제 근거 필수. 기존 은행·지급 사건을 수기 원본으로 바꿔 중복 등록하는 우회 금지. |

기존 은행 거래 유일 인덱스는 유지한다. 최초 지급 전표에만 기존 `bank_transaction_id`를 연결하고, 역분개·대체분은 원전표와 사건 연결을 통해 은행 거래로 추적한다. 이체·카드·기존 전표의 사건 연결도 같은 조직 잠금 아래 중복 검사한다.

금액 타입도 확인해야 한다. 현재 전표 행은 `numeric(14,0)`, 통합 지급은 `numeric(16,0)`, 일부 간편지출은 소수 금액을 허용한다. 새 연결에서 조용히 반올림·절삭하지 않는다. 기존 값과 허용 최대금액을 조사한 뒤 정밀도를 맞추거나 전표 저장 시 명시적으로 범위/원 단위를 검증한다.

지급 700 중 A 250/B 150만 배분된 경우, 미배분 300을 임의 비용으로 채우지 않는다. 초안/검토는 허용하고 기본 확정은 배분 완료까지 제한한다. 운영에서 미배분 자금의 임시 계정 처리를 실제 승인하면 별도 명시적 계정/근거로 300을 분개하고 이후 배분은 현금 재인식 없이 재분류한다. 해당 정책을 확인하기 전에는 자동 가계정 생성 금지.

## 상태 전환과 저장 원칙

| 현재 | 명령 | 결과 / DB 검증 |
| --- | --- | --- |
| 없음 | 초안 생성 | 원본·조직 확인, 업무 중복키 확보, 헤더/분개/링크/감사를 원자적으로 저장. 계정 미확정은 초안 가능. |
| 초안 | 저장 / 검토 요청 | expected lock_version 검사. 선택 계정의 조직 확인. 저장 실패 시 이전 분개 유지. |
| 검토 중 | 초안으로 반환 | 사유·검토자 기록. 내용 수정 후 재검토. |
| 검토 중 | 확정 | 차변 합=대변 합>0, 각 행 한쪽 금액만 양수, 계정 필수·활성·동일 조직, 원본 최신 지문/금액/배분 확인. 날짜와 기간 정책 확인. |
| 초안/검토 중 | 취소 | 사유와 당시 내용 보존. 물리 삭제 금지. 해당 사건 재작성은 새 전표를 무제한 추가하지 않고 명시적 재작성 버전 처리. |
| 확정 | 정정 시작 | 원분개 수정 금지. 역분개+대체 초안을 같은 정정 사건으로 생성. 확정 전까지 기존 회계 실적 유지. |
| 정정 검토 중 | 정정 확정 | 역분개 및 대체전표를 함께 원자적으로 확정. 중간에 원전표만 무효화되어 잔액이 사라지지 않도록 한다. 단순 취소라면 사유 있는 역분개만 확정. |

원전표는 역사적 확정 상태·분개를 유지하고 파생 표시 `정정됨/역분개됨`을 추가한다. 집계는 확정된 원분개+역분개+대체분을 합산한다. 원전표를 집계에서 제외하면서 역분개까지 합산하는 이중 차감 금지.

원본 금액·귀속일·수취인 변경 또는 지급 배분 취소는 확정 전표를 자동 갱신하지 않는다. 차이와 정정 필요 상태를 표시하고 신규 확정을 막는다. 이미 확정한 실제 입출금 자체는 삭제되지 않는다. 배분 취소가 지급 사실 취소인지 분류 정정인지는 원래 사건과 실제 은행 기록으로 구분한다.

## 권한과 미확정 정책

현재 역할은 `ADMIN/APPROVE/SENIOR/CLOSE/PAY`뿐이며 회계 전용 권한은 없다(`reimbursement-domain.ts:1`). 지급 권한만 있다는 이유로 회계 확정 권한까지 부여하지 않는다.

아래는 현재 시스템에 이미 존재하는 권한 매핑이 아니라 신규 회계 기능의 제안이다. 저장소에서 승인된 회계 담당 범위가 추가로 확인되면 그 근거를 우선해 재사용하고, 미확정 부분만 설정으로 제한한다.

| 업무 | 구현 가능한 보수적 기본값 | 정책 확인 이후 확장 |
| --- | --- | --- |
| 회계 전체 조회 | 기존 업무 담당 역할의 조직 범위 조회; 일반 신청자는 자기 원본과 연결된 최소 결과만 | 세부 회계정보 열람 범위 |
| 원본 연결 초안/계정 검토 | ADMIN, APPROVE에 초안·검토 기능. PAY는 지급에서 회계 미처리 조회/연결 이동 | 회계 담당자별 작성 권한 |
| 확정·수기·역분개 | 회계권한 정책 미확정 시 실행 제한. ADMIN도 계약/회계 정책을 자동으로 대체하지 않음 | 기존 역할 중 명시적으로 승인된 확정자 설정. 작성자와 확정자 분리 여부 명시 |
| 기간 잠금 | 마감 점검과 미처리 목록은 구현 | CLOSE는 기존 개인 정산 권한이며 전체 회계 기간 잠금 권한으로 자동 확대하지 않음 |

계정 선택/차대 균형/원본 검토 기능은 독립적으로 구현한다. 비용·사업원가·자산, 납입금의 부채/수익, 부가세 공제·불공제, 자금이체 임시 계정, 소급 귀속 및 회계기간 잠금은 실제 정책이 확인되어야 해당 자동 처리·확정에 사용한다. 실사용일 3월/실제 환급 6월은 별도 필드로 유지하고 6월 지급을 3월 지급으로 위조하지 않는다.

## 금액 예제

금액은 단순화한 원 단위이며 예제 계정은 사람이 해당 거래에 적합하다고 확인한 경우다. 세무 판단이나 계정 자동 매핑 규칙이 아니다.

1. 업무 사용 1,000, 지급 400+600: 발생에 차변 비용/자산 등 선택계정 1,000, 대변 미지급금 1,000. 첫 지급은 차변 미지급금 400/대변 예금 400, 다음은 600/600. 총 비용 인식은 1,000이고 지급 때문에 2,000이 되지 않는다.
2. 3월 직원 대납 100, 6월 환급 100: 사용 사건의 선택 귀속일에 비용/자산 100 대변 직원 미지급금 100. 6월 실제 지급은 미지급금 100/예금 100. 3월 마감이 닫혀 있으면 회계 정책에 따른 조정일을 따로 선택하며 실사용일은 3월로 남긴다.
3. 선지급 1,000 후 인정 사용 800, 실제 반납 200: 지급 차변 선급/가지급 해당계정 1,000 대변 예금 1,000. 사용 정산 비용/자산 800 대변 선급 해당계정 800. 실제 반납 예금 200/선급 해당계정 200. 선지급 잔액은 0, 비용은 800. 인정 사용이 1,200이면 추가 미지급금 200을 인식하고 실제 추가 지급과 연결한다.
4. 관리계좌→운영계좌 1,000: 차변 운영 예금 1,000 대변 관리 예금 1,000. 실제 비용·납부 실적 증가 0. 신탁의 계좌 이동 승인만 있고 입출금 사실이 없으면 확정 자금이체 전표를 생성하지 않는다.
5. 현금 700 지급, A 채무 250/B 채무 450: 차변 미지급금 A 250, B 450 / 대변 예금 700. 전표 1건에 배분 링크 2건. A 발생전표와 B 발생전표의 비용을 지급 전표에서 다시 차변 비용으로 생성하지 않는다.
6. 확정 비용 1,000의 계정 오류: 원전표 1,000 유지, 역분개 -1,000, 대체 올바른 계정 +1,000. 순인식은 1,000. 원전표를 조회에서 삭제하지 않는다.

## 다음 구현을 나누는 단위와 완료 기준

### A. 실제 전표 조회와 연결 초안

- 기존 전표/계정 조회 repository, `/finance` 실제 목록·상세, 원본/지급에서 초안으로 연결.
- 기존 전표는 번호·분개를 변경하지 않고 `기존 기록·검토 필요`로 식별; 발생/지급 의미를 번호만으로 추측하지 않음.
- RPC 생성/저장/검토, 업무 중복키, org/actor 검증, 초기 회계권한 설정 필요 상태.
- 저장→재조회→새로고침 내용 일치. 권한 없는 사용자/다른 조직 원본·계정·전표 차단. 동시 초안 생성 2세션에서 1건. 같은 키 재시도 1건, 다른 입력 충돌. 중간 실패 시 기존 행 보존.

### B. 확정·정정 및 기존 경로 통합

- 계정/균형/금액/원본 버전·지급 배분 확인, 실제 정책을 근거로 한 확정 권한 설정.
- 확정 헤더·분개·원본 링크 보호 트리거, 단일 RPC 역분개/대체, 전표 채번 DB화.
- `transitionExpenseDisbursementAction`의 전표 명령을 신규 RPC에 위임하고 기존 `syncExpenseVoucherRecords` 우회 경로 제거. 결의 화면의 버튼·표시는 여러 연결 전표를 읽도록 보완하고 기존 전표번호는 보존.
- 확정 후 직접 update/delete 및 legacy action 우회 차단. 확정/정정 동시 실행, 이중 역분개, 잘못된 날짜·비균형·null계정·다른조직 계정 실패. 실제 회계 집계 원+역+대체 금액 검증.

### C. 정산·수납 확장과 운영 적용

- 현재 실제 구현된 원본은 RESOLUTION/QUICK/PERSONAL. ADVANCE/COLLECTION/REFUND/CARD 사건은 고유 원본 및 정책 연결이 구현된 후 확장하며 문자열만 받아 지원하는 척하지 않는다.
- 기존 간편지출·개인 정산이 같은 사용이면 명시적 ID 연결 후 최초 인식 1회. 이름·동일 금액·날짜로 자동 병합 금지.
- 지급/카드대금/이체의 현금 기록, 예산 원장, 납부 실적, 회계 실적은 각각 검증한다. 전표 확정으로 예산 집행이나 수납 금액 자동 증가 금지.
- 독립 Postgres 실제 SQL, repository/Auth, UI 저장·재조회·권한, 운영 전후 원본 건수·금액·분개·첨부 지문 확인. DB 적용 및 배포 여부는 커밋/푸시와 별도 보고.

이 설계의 조사·문서 작성은 완료했으며 A~C 구현과 운영 적용은 아직 완료한 것으로 보고하지 않는다.
