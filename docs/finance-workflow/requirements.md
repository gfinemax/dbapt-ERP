## 1. 목표와 진행 원칙

사용자가 지출 등록부터 내부 결재, 신탁 집행요청, 실제 지급, 정산, 회계 처리까지 같은 거래를 중복 입력하지 않고 처리하도록 만들어줘.

다음 업무는 독립적인 상태와 근거를 가지되 서로 연결돼야 한다.

- 조합 내부 결재
- 신탁사의 자금집행 심사
- 실제 지급
- 개인 대납·선지급 정산
- 회계 처리
- 예산 집행
- 증빙 확인

기안 생략, 정식 지출결의서 생략, 신탁 심사 대상 아님은 서로 다른 조건이다. 하나를 선택했다고 나머지를 자동 생략하지 마.

사소한 구현 선택은 기존 프로젝트 관례에 따라 진행해줘. 실제 계약이나 회계 정책이 필요한 부분은 임의로 확정하지 말고 설정 필요 항목으로 남겨줘. 해당 사항과 독립적으로 진행할 수 있는 구현은 계속해줘.

## 4. 업무현황과 상세 화면

업무현황을 단순 통계 화면이 아니라 담당자가 다음 작업을 시작하는 화면으로 만들어줘.

현재 사용자 권한에 따라 다음 처리 대상을 보여줘.

- 내가 결재할 건
- 신탁 요청 준비 대상
- 신탁사가 보완 요청한 건
- 지급 조건을 충족한 미지급 건
- 정산 기한이 지난 건
- 증빙 보완이 필요한 건
- 미매칭 계좌 거래
- 회계 처리 또는 마감 점검이 필요한 건

실제 원천 데이터로 집계하고, 클릭하면 해당 조건이 적용된 목록으로 이동하게 해줘. 건수와 목록 결과가 일치해야 한다. 날짜 기준과 상태 조건을 명확히 표시하고 빈 데이터에 예시 건수를 넣지 마.

신탁 심사 중인 거래를 지급 가능한 거래와 섞지 마.

지출 상세 화면에서는 다음 정보를 연결해서 확인할 수 있도록 해줘.

- 기본정보·계약·예산·증빙
- 내부 결재
- 신탁 요청·회신
- 실제 지급 내역
- 정산·회계전표
- 변경 이력

권한과 현재 상태에 맞게 ‘결재하기’, ‘신탁 요청에 추가’, ‘보완하기’, ‘지급 내역 연결’, ‘정산하기’ 등 다음 작업을 제공해줘. 모든 업무를 처리하기 위해 사이드바를 반복 이동해야 하는 구조를 피하고, 별도 메뉴는 여러 건을 모아서 처리하는 데 활용해줘.

## 5. 지출 등록 단순화

지출관리에서 정식 결의, 간편지출, 선지급·정산을 함께 조회하되 각 기록의 성격을 구분해줘.

간편지출이 이미 독립적으로 구현돼 있으면 재사용해줘. 정식 결의가 필요 없는 거래를 등록할 때 정식 결의서를 자동 생성하지 마.

작성 화면의 첫 선택은 다음과 같이 구성해줘.

- 앞으로 지급할 거래
- 이미 사용하거나 지급한 거래
- 먼저 지급한 돈의 정산

선택한 상황에 필요한 입력만 단계적으로 보여줘.

다음 항목은 서로 다른 축으로 관리해줘.

- 승인 근거: 승인된 기안, 승인 예산·위임 규정, 정기 계약, 사후 승인 등
- 지급 방식: 거래처 지급, 직원 대납 환급, 법인카드, 현금, 선지급 등
- 집행 경로: 신탁사 직접 집행, 계약상 허용된 운영계좌 집행 등
- 등록 방법: 직접 입력, 증빙에서 입력, 기존 거래에서 가져오기
- 작성 단위: 단일 거래 또는 여러 항목 묶음

‘직접 입력’과 ‘예산 내 간편지출’을 같은 분류의 선택지로 두지 마.

작성자, 거래상대방, 실제 지급 수취인을 구분해줘. 거래처 지급 건의 수취인을 로그인 사용자로 임의 지정하지 마.

작성일·거래일·회계 귀속일·지급예정일·실제 지급일을 구분해줘. 실제 지급일은 지급 기록에 연결하고, 지급 전 거래에 오늘 날짜를 자동 입력하지 마.

예산 미선택을 승인 예산 내 지출로 확정하지 마. 업무 근거 없는 금액·횟수·비율을 고정 기본값으로 넣지 마.

## 6. 신탁 자금집행 관리

법적 자금보관 의무와 개별 계약의 집행 조건을 구분해줘. 관련 법령은 현재 유효한 공식 자료로 확인하고, 저장소에 실제 자금관리 계약서·신탁사 요청 양식이 있으면 검토해줘.

계약 자료가 없다면 필수서류, 공동 동의자, 운영비 선교부 가능 여부, 집행 한도를 임의로 확정하지 마. 설정 가능한 구조와 ‘설정 필요’ 상태를 제공해줘.

신탁 대상 여부는 관리계좌·계약·거래 조건과 연결하고, 담당자가 근거 없이 우회하는 단순 체크박스로 만들지 마.

첫 버전은 외부 신탁사 시스템 연동 없이 담당자가 제출·회신 결과를 기록하는 방식으로 구현해줘.

필수 기능:

- 기존 지출을 선택하여 집행요청서로 묶기
- 항목별 요청금액
- 요청번호·요청일·대상 신탁사·관리계좌·접수정보
- 요청서 출력 또는 다운로드
- 제출 당시 요청 내용과 첨부서류 버전 보존
- 회신 첨부와 보완 사유
- 항목별 승인·일부 승인·보완·반려
- 보완 후 재제출
- 철회·변경 이력
- 실제 지급 연결

요청 전체 상태와 항목별 결과를 구분해줘.

신탁 상태:
요청 준비 / 제출 / 심사 중 / 보완 요청 / 일부 승인 / 승인 / 반려 / 철회

신탁 승인만으로 실제 지급이나 회계 비용을 생성하지 마.

금액은 다음과 같이 구분해줘.

- 지출 확정액
- 이번 요청액
- 유효한 승인액
- 누적 실제 지급액
- 총 미지급액
- 승인액 중 미지급액
- 추가 요청 가능액

부분 승인·재제출·철회 시 금액을 중복 합산하지 않도록 규칙을 정의해줘. 이미 요청 중이거나 승인·지급된 금액의 중복 요청을 서버에서도 방지해줘.

제출 후 금액·수취인·계좌 등 중요 정보가 변경되면 기존 제출본을 보존하고 재검토 대상으로 처리해줘.

## 7. 지급·정산·수납 연결

다음을 지원하도록 기존 기능을 보완해줘.

- 한 지출을 여러 번 나눠 지급
- 한 지급을 여러 지출에 배분
- 신탁사 직접 지급
- 직원 대납 환급
- 선지급 후 사용액 정산
- 잔액 반납·추가 지급
- 과지급 회수
- 지급 취소·환급

지급관리의 완료 상태는 실제 지급 근거와 연결해줘. 이미 사용한 카드 거래, 직원 대납, 실제 계좌 출금은 각각 구분하고 중복 지급 요청을 막아줘.

동일 조합의 신탁 관리계좌에서 운영계좌로 이동한 돈을 실제 사용 비용과 중복 집계하지 마. 운영비 선교부는 계약상 허용 여부와 정산 조건이 설정된 경우에만 사용할 수 있게 해줘.

이미 출금된 거래는 내부 결재나 신탁 심사가 반려돼도 삭제하지 마. 후속 소명·정정·회수와 연결해줘.

분담금 수납은 조합원 고유 식별자와 납부 항목·회차에 연결하고, 이름만으로 자동 확정하지 마. 예치기관에서 신탁 관리계좌로 이동한 자금을 조합원 신규 납부로 중복 반영하지 마.

환급은 원래 납부, 반환 결정, 필요한 신탁 요청, 실제 환급을 연결해줘. 기존 환급 산정·승인 규칙은 근거 없이 변경하지 마.

## 8. 전표·예산 처리

현재 회계 구조를 확인한 뒤 확장해줘.

- 복식부기 구조가 있으면 기존 모델과 연결을 보완한다.
- 입출금 기록만 있으면 이를 회계전표로 오인하지 않도록 구분하고 필요한 전표 구조를 단계적으로 추가한다.
- 거래 인식과 실제 지급을 분리한다.
- 미지급금·선급금·자금이체 등을 처리할 수 있게 한다.
- 카드 사용과 카드대금 출금, 직원 대납과 환급에서 비용을 이중 생성하지 않는다.

전표 화면에서 지출 등록을 시작해도 공통 지출 작성으로 연결해줘. 기존 지출·수납·지급·계좌 거래에서 전표를 작성할 때 원본 연결을 유지하고 중복 생성을 방지해줘.

수기·정정 전표는 권한과 사유를 관리해줘. 확정 기록은 이력 없는 덮어쓰기 대신 취소·정정 절차로 수정해줘.

토지비·공사비·설계비를 모두 즉시 비용으로, 분담금 입금을 모두 매출로 자동 처리하지 마. 검증된 회계 정책이 없으면 계정 매핑과 검토 절차를 제공해줘.

다음 실적을 구분해줘.

- 조합원 납부 실적
- 실제 입출금
- 예산 집행
- 회계상 수익·비용·사업원가·자산·부채

예산은 확정 예산, 예약액, 집행액, 사용 가능액을 구분하고 예약에서 집행으로 전환될 때 두 번 차감하지 마.

집행 인식 시점과 부가세 포함 여부는 기존 정책을 확인해 일관되게 적용하고 화면에 기준을 표시해줘. 신탁 승인액을 예산 집행액으로 자동 간주하지 마.

## 9. 데이터 보존과 접근제어

기존 문서번호, 기안 연결, 결재 이력, 증빙 파일, 지급액, 전표, 정산 기록을 보존해줘.

- 과거 신탁 정보가 없으면 ‘확인 필요’로 처리
- 과거 지급완료 건을 다시 지급대기로 전환하지 않음
- 확인되지 않은 지급·승인 기록을 추정 생성하지 않음
- 데이터 전환 전후 건수·금액·연결·증빙 보존 대조
- 조직별 접근제어와 역할 권한을 서버·DB 수준에서 적용
- 새 테이블에도 실제 접근 정책 적용
- 동시 요청과 중복 클릭에서 이중 생성·집행 방지
- 제출·승인·지급·정정 행위의 담당자와 시각 기록

운영 데이터 삭제나 되돌리기 어려운 전환이 필요하면 영향 범위, 전환 미리보기, 복구 방안을 먼저 준비한 후 해당 작업만 승인을 요청해줘.

## 10. 구현 순서와 검증

권장 순서:

현재 구조 조사
→ 업무·상태·금액·원본 연결 설계
→ 공통 데이터와 지급 배분 보완
→ 신탁 집행관리
→ 지출 작성·상세·업무현황 개편
→ 사이드바와 기존 경로 통합
→ 데이터 호환성과 통합 검증

사이드바 이름만 바꾸고 기능 연결을 미완성으로 남기거나, 동작하지 않는 메뉴를 완료 기능처럼 노출하지 마.

다음 시나리오를 중심으로 의미 있는 테스트와 가능한 브라우저 검증을 수행해줘.

- 기안 연결 지출
- 정식 결의 없는 간편지출
- 개인 대납 후 환급
- 선지급 후 반납·추가 지급
- 법인카드 사용과 카드대금 출금
- 신탁 요청 중 일부 항목 보완
- 일부 승인 후 분할 지급
- 철회·반려 후 재요청
- 한 지급의 여러 지출 배분
- 신탁계좌와 운영계좌 간 이동
- 분담금 수납·환급 연결
- 중복 제출·동시 처리
- 권한 없는 조회·상태 변경 차단
- 기존 증빙·출력·집계 보존
- 저장 후 재조회·새로고침 결과
- 업무현황 건수와 클릭한 목록의 일치
- 사이드바 그룹·순서·활성 상태·모바일 표시
- 기존 지급대기·지급완료 URL의 대응 탭 연결

운영 환경에서 검증용 송금·신탁사 제출·결재·이메일 발송을 하지 마. 변경 검증은 테스트 환경과 안전한 테스트 데이터로 수행해줘.

관련 테스트, 정적 검사, 빌드 등 필요한 검증을 수행하고 기존 실패와 이번 변경의 실패를 구분해줘.

검증이 끝나면 이번 작업 범위만 커밋하고 원격에 푸시해줘. 저장소의 보호 브랜치·배포 규칙을 따라줘. 푸시 성공을 운영 배포 성공으로 간주하지 말고 실제 확인한 범위를 구분해줘.

최종 보고에는 다음을 간단히 정리해줘.

- 바뀐 사이드바와 업무 흐름
- 구현한 주요 기능
- 기존 데이터·기능 보존 결과
- 검증 결과와 미검증 항목
- 신탁 계약·회계 정책 확인이 필요한 설정
- 마이그레이션 적용 여부
- 커밋·푸시·배포 상태

전체 목표는 유지하되 단계별 완료 기준을 정하고 순서대로 구현해줘. 조사 결과에 따라 기존 기능 재사용, 신규 개발, 정책 확인 필요 항목을 구분해줘. 구현 전에 원본 연결 구조, 상태 전환표, 금액 계산 예제, 기존 URL·메뉴 대응표를 작성해줘. 정책 미확정 항목은 해당 정책에 의존하는 실행만 제한하고 독립적인 작업은 계속해줘. 각 단계는 저장·재조회·권한·중복 처리 검증을 완료한 단위로 커밋하고, 미완료 단계와 운영 적용 여부를 명확히 보고해줘.
