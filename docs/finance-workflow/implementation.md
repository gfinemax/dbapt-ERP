## 1단계 구현

- 기존 결의/간편지출/개인 정산 원본은 유지하고 조직+원본 유형+원본 ID로 연결한다.
- 과거 지급완료인데 금액이 없으면 지급액을 추정하지 않는다. 기존 완료 표시와 확인 필요를 함께 유지한다.
- 실제 은행/현금 지급 기록과 지출 배분을 분리한다. 한 지급의 여러 지출 배분, 분할지급, 원지급에 대한 반환, 배분 정정 이력을 지원한다.
- 계약 미설정은 지급 배분 실행만 제한한다. 원본 조회·연결·실제 입출금 기록은 가능하다.
- 은행 원본 ID, 현금 지급 증빙 ID, 조직별 처리키로 중복 등록을 막는다. DB 잠금으로 동시 잔액 초과를 막는다.
- 이전 경로가 통합 연결된 지급액을 직접 덮어쓰거나 원은행 거래를 바꾸지 못하게 DB 트리거로 제한한다. 이 트리거는 원본을 실제로 연결한 뒤 적용된다.
- 같은 조합의 계좌이체를 비용·새 납부·예산 집행으로 생성하지 않는다.
- API에서 사용자/조직을 입력값으로 신뢰하지 않고 기존 Auth 검증과 구성원 조회를 재사용한다. DB 명령도 권한을 재검사한다. 신규 테이블은 서비스 경로 전용 정책과 권한을 적용한다.

## 2단계 진행: 신탁 저장·처리 기반

2단계는 저장·처리 기반(2a)과 실제 업무 화면 연결(2b)로 검증 단위를 나눈다. 화면까지 연결하기 전에는 2단계 전체 완료로 표시하지 않는다.

- 계약 초안/확인/폐기/새 버전, 관리계좌·운영계좌·적용 거래·필수서류·공동동의·한도·운영비 선교부 조건을 저장한다. 정책 미확정 초안은 저장 가능하며 제출/집행에만 확인 조건을 적용한다.
- 확인된 계약과 참조 계좌의 중요정보는 보존한다. 변경은 새 계좌/계약 버전으로 남긴다.
- 요청과 항목을 저장하고, 제출 시 계약/내부 승인/중복 요청액을 DB에서 확인한다. 원본과 계약, 선택 항목, 첨부 해시를 제출 버전으로 고정한다.
- 항목별 부분승인·보완·반려와 보완 항목만 재제출, 철회 요청/확인을 지원한다. 철회 확인 전에는 예약을 해제하지 않는다.
- 원본 감액 이후에는 자기 예약까지 포함한 전체 잔액으로 재제출 한도를 검사한다. 일부 지급 후 재검토는 기존 실제 지급을 보존하고 미지급 부분만 예약한다. 신탁사 회신은 당시 제출본의 사실로 보존하고 현재 원본이 달라지면 추가 지급을 제한한다.
- 요청 번호와 초안/제출본 인쇄 경로를 제공한다. 재제출 출력은 이번에 선택한 항목만 포함하며 원본 문서번호와 마스킹 계좌를 사용한다. 요청 전체 감사 스냅샷은 별도 보존한다.
- 첨부는 3MiB 이하 실제 PDF/PNG/JPEG/WebP 바이트를 검사하고 비공개 저장소에 덮어쓰기 없이 저장한다. 재시도는 기존 바이트의 SHA-256 일치까지 확인한다. 메타데이터 저장이 불명확한 경우 파일을 삭제하지 않는다. 다운로드는 조직/역할 확인 후 60초 서명 링크로 제공한다.
- 업로드/서명 링크는 공식 SDK 문서를 확인하여 구현했다: [업로드](https://supabase.com/docs/reference/javascript/file-buckets-upload), [다운로드 서명 링크](https://supabase.com/docs/reference/javascript/file-buckets-createsignedurl).

현재 검증: 관련 도메인/저장소/첨부/출력 단위 테스트 155개와 출력 HTTP 경로 테스트 24개 통과, 변경 파일 ESLint 통과. 프로덕션 빌드도 통과했다(미커밋 기존 화면 초안 포함). 별도 TypeScript 검사에서 신규 파일 오류는 수정했으며 기존 14건은 남아 있다. 격리 PostgreSQL에서 기존 SQL 회귀와 신탁 저장·재조회·권한·버전 잠금·혼합 회신·재제출·철회·감액·부분지급 재검토를 통과했다. 별도 동시 세션에서 1,000원 거래에 600원 요청 두 건 중 하나만 제출되고 같은 처리키 재시도에도 제출본 하나만 유지되는 것을 확인했다.

미검증/미완료: 실제 Storage 서비스와 브라우저 업로드, 요청·계약 설정 업무 화면, 운영 마이그레이션/배포. 운영 DB에는 새 기반을 적용하지 않았다.

## 2b 구현: 신탁 요청·계약 설정 화면

- `/finance/trust`에서 기존 결의·간편지출·개인 정산의 고유 ID를 선택하여 연결하고, 요청 초안 저장·재조회·항목별 제출·회신·보완·철회·첨부·버전별 출력을 제공한다. 원본 선택은 유형별 최근 100건 범위를 표시한다.
- `/finance/workflow-settings`에서 계약 초안을 저장하고 관리자만 계약 확인·폐기·새 버전 등록을 실행한다. 미확정 조건은 임의 기본값으로 확정하지 않는다.
- 실패한 입력과 재시도 처리키를 유지하고 이중 클릭을 제한한다. 편집 중 외부 변경이 생기면 기존 잠금 버전을 유지하여 덮어쓰기를 거절한다. 경로 변경도 원본 버전을 증가시켜 동시 편집 충돌을 감지한다.
- 기존 로그인 화면은 선택적 제목/설명만 추가하여 재사용한다. 미완성 사이드바 초안은 이 커밋에서 제외한다.

검증: 화면·설정·원본 조회 3개 파일 27개 테스트 통과, 변경 파일 ESLint 통과, 프로덕션 빌드 통과. 격리 PostgreSQL 전체 SQL 회귀, 저장·재조회·권한·중복·동시 실행 검증 통과. 넓은 기존 Storage 정책이 있어도 신규 비공개 버킷은 일반 DB 역할에 노출되지 않는지 검증했다. 별도 TypeScript 검사에는 기존 오류 14건이 남아 있으며 신규 파일 오류는 없다. 빌드에는 기존 미커밋 화면 초안도 포함되어 전체 메뉴 완료의 근거로 사용하지 않는다.

남은 일: 실제 로컬 Storage 업로드와 브라우저 통합 검증, 3단계 회계·정산·수납, 4단계 공통 화면·메뉴, 5단계 통합·운영 적용. 운영 DB 마이그레이션과 운영 배포 확인은 수행하지 않았다. 메인 푸시는 운영 적용 완료를 의미하지 않는다.

## 3a 구현: 실제 지급 화면 연결

- `/finance/payments`에서 실제 은행·현금 기록, 여러 지출에 대한 배분, 원지급을 지정한 반납·회수, 사유 있는 배분 취소 이력을 제공한다. 기존 단계 1의 잠금·중복 방지·원본 보존 명령을 재사용한다.
- 지급가능/지급대기/부분지급/지급완료/확인 필요/과지급 탭과 검색을 같은 조회 결과로 계산한다. DB가 최신 원본·내부 승인·계약·신탁 승인 버전과 잔액을 확인한 지급 가능액을 표시한다. 실제 은행 근거와 금액은 실행 시 다시 검증한다.
- 기존 지급완료 기록의 금액을 추정하거나 지급대기로 되돌리지 않는다. 이체는 별도 실제 내역으로 조회하고 지급·비용에 중복 합산하지 않는다. 조회 역할에도 이체 이력을 제공하며 지급 권한이 있어야 변경할 수 있다.
- 은행 선택은 미연결 최근 200건과 마스킹 계좌만 표시한다. 현금 증빙은 기존 비공개 파일 저장 경로를 재사용한다. 현금 입력 시각은 한국 시간으로 명시 변환한다.
- 신탁 화면에서 지급 가능한 거래로 이동할 수 있다. 기존 지급대기·완료 URL 통합은 전체 원본 조회/메뉴 단계에서 수행하며 현재 경로를 제거하지 않는다.

검증: 지급 도메인·저장소·화면 30개 테스트 통과, ESLint 통과. 격리 PostgreSQL 전체 회귀와 새 지급 조회 테스트에서 저장·재조회·권한·계좌 마스킹·미래/다른 조직 은행 제외·부분지급·반납/정정 보존·요청 중 예약·변경 승인 제외·중복/동시 처리 통과. 프로덕션 빌드 통과, 별도 TypeScript 검사는 기존 14건이 남아 있고 신규 지급 파일 오류는 없다. 실제 Storage/브라우저 통합 검증은 별도로 진행 중이다. 운영 DB에는 적용하지 않았다.

회계 연결 조사와 원본·상태·금액 예제는 `accounting-design.md`에 작성했다. 회계 확정 권한은 별도 정책 확인 대상이며 초안·조회 개발과 분리한다.

## 3b 구현: 기존 복식전표 조회·연결 초안과 선지급 원본 검증

- `/finance`에서 조직의 실제 기존 전표·분개·계정을 조회한다. 기존 번호와 승인 상태를 유지하고, 원본이 없는 전표를 발생/지급 전표로 추정하지 않는다.
- 거래 발생/실제 지급/계좌이체 원본에 최초 전표를 하나만 연결한다. 지급 1건의 여러 배분은 하나의 지급 전표 원본 스냅샷에 보존한다. 간편지출→결의, 개인 대납→간편지출의 명시적 ID 관계도 양방향 중복을 검사한다.
- 초안의 헤더·분개·원본·감사를 하나의 DB 명령으로 저장한다. 계정 미확정이나 차대 차이는 초안으로 보관하되 잘못된 조직의 계정/원본·소수/범위 초과 금액은 거절한다. 원본 확인 불가 한 건이 전체 기존 전표 조회를 막지 않는다.
- 기존 전표 액션은 원본 변경 전에 통합 관리 여부를 확인한다. DB에서도 새 전표 번호를 통한 중복 생성과 통합 초안·원본 전표 상태의 직접 변경을 차단한다. 초안 편집 중 다른 저장이 있으면 입력을 유지하고 재조회를 요구한다.
- 회계 확정·수기·정정 권한은 확인 요청 중이다. 해당 실행을 제공하지 않고 조회·연결·계정 검토는 계속 제공한다. 초안이 예산·입출금·회계 확정 실적을 만들지 않는다.
- 기존 선지급 정산 후보를 담당자 선지급으로 한정했다. 승인 총액·작성일을 실제 지급액·일자로 대체하지 않는다. 미확정 초안과 과거 기록은 유지하고 신규 승인/실제 지급 전환에서는 같은 조직의 typed 지급액·지급일을 검증한다. 통합 지급에 배분된 원본의 과거 정산 경로 재사용은 차단한다. 이 수정은 선지급 통합 정산 전체의 완료가 아니다.

검증: 회계 UI 10개, 저장소 14개, 기존 액션 쓰기 전 차단 3개 테스트 통과. 선지급 helper/기존 도메인 21개 테스트 통과. 전체 격리 SQL 회귀와 새로운 회계/선지급 SQL 검증 통과, 실제 별도 세션의 동일 원본 회계 초안 동시 생성은 1건만 성공하고 같은 처리키 재시도는 같은 전표를 반환했다. 프로덕션 빌드 통과, 신규 파일 ESLint 오류 없음. 별도 TypeScript는 기존 14건 오류를 유지하며 신규 회계/지급 오류는 없다. 실제 브라우저 검증 범위는 `local-integration-verification.md`에 별도로 기록한다.

남은 단계: 회계 확정·정정 정책과 구현, 통합 선지급 사용·반납·추가지급 정산, 수납/환급 원장 연결, 공통 지출·업무현황·전체 메뉴 통합, 운영 데이터 대조와 마이그레이션/배포 확인. 운영 DB에는 이번 마이그레이션을 적용하지 않았다.

## 4a 구현: 공통 지출 원본 조회·연결

`expense-workspace.md`에 상세 범위와 기존 작성 화면 연결을 기록했다. 원본 종류·통합 연결·검색·고유 ID 상세와 신탁/회계 연결을 제공한다. 별도 신규 지출을 만들지 않고 기존 ENROLL 명령을 재사용한다. 일반 신청자는 본인 개인 대납 자료만 조회한다.

검증: 화면/저장소/액션 15개 테스트와 ESLint 통과. 격리 SQL 전체 회귀에서 원본 105건 조회, 조직·소유자 권한, 원본 지문 보존, 연결 저장·재조회·중복 처리, 회계/신탁 링크 통과. 프로덕션 빌드 통과. 실제 로컬 브라우저에서 원본 선택→연결→새로고침 후 원본 JSON 동일·연결 1건을 확인하고 기존 회계전표 링크 이동을 확인했다.

미완료: 모든 작성·결재를 공통 화면에서 직접 처리하는 통합 편집기, 선지급 통합 정산, 전체 메뉴·업무현황 후속 검증, 운영 마이그레이션/배포. 운영 파일 읽기 검증에서 기존 증빙 4개 모두 다운로드 가능했고 총 899,566바이트의 SHA-256 기준을 로컬 비공개 검증 기록에 저장했다. 기존 결의/간편지출/전표/증빙 메타데이터 지문도 시작 기준과 일치했다. 운영 업무 데이터를 변경하지 않았다.

## 기존 결의서 신규 입력 기본값 보완

새 결의서에서 실제 지출일·선지급일·지급예정일은 빈칸으로 시작한다. 작성일과 실제 지급 사실을 구별하며, 수취인 계좌는 수동 입력 상태로 시작해 특정 직원의 예시 계좌를 자동 지정하지 않는다. 기안 생략 사유도 명시적으로 선택한다. 기존 결의 수정 시 없는 실제 지출일을 작성일로 대체하지 않으며 저장된 날짜·계좌는 보존한다.

검증: 기본값 회귀와 기존 작성·수정·증빙·계좌 저장/재조회 UI 35개 테스트 통과. 기존 계좌 저장 테스트는 예금주를 명시 입력하도록, 필수 항목 이동 테스트는 생략 근거를 명시 선택하도록 변경했다. ESLint 오류 없음(기존 미사용 변수 경고 1개). 이 변경은 기존 결의서의 고정 사용자·예시 지급대상 목록·모든 승인 권한 구조를 정비한 완료 단계는 아니며 해당 원본 작성기 통합은 후속 작업이다.

## 3c 구현: 담당자 선지급 정산 초안

`advance-settlement-implementation.md`에 원본 연결·금액 예제·정책 잠금과 미완료 범위를 기록했다. 확인된 실제 선지급 배분을 최초/추가로 명시 분류하고 사용 원본·기존 증빙을 연결해 초안을 저장한다. 실제 반납을 원지급 배분에 따라 한 번만 차감하며 차액이 0이어도 정산완료를 자동 생성하지 않는다.

검증: UI/저장소/action 21개 테스트 통과. 배경 변경 후 직접 form submit도 실행하지 않는 회귀 포함. 격리 PostgreSQL에서 원본·예산·지급 불변, 원자적 저장·재조회, 조직·역할, 원본/증빙 중복, 같은 처리키, 반납·추가지급·역분개 산식 검증 통과. 실제 두 세션에서 같은 사용 원본을 서로 다른 선지급 초안에 예약하면 하나만 저장된다. 최종 프로덕션 빌드 통과. 실제 브라우저 결과는 local-integration-verification.md에 별도로 기록한다.

정산 확정·회계/예산 반영·추가지급 실행·정산 회차·담당자 UUID 소유권은 후속 범위이며 정책 확인 없이 활성화하지 않았다. 운영 migration은 미적용이다.

## 4b 구현: 업무현황·검토 메뉴·기존 URL 연결

`navigation-implementation.md`에 15개 메뉴·현재 기능 범위·URL 대응·남은 작업을 정리했다. 업무현황은 11개 분류의 실제 원천을 조회하며 각 카드의 목록을 같은 자료로 계산한다. 본인 기안은 Auth UUID에 지정된 현재 결재 순서만 포함하고, 조직 승인대기 지출과 구분한다. 예상 밖 조회 실패를 실제 0건으로 대체하지 않는다.

기존 지급대기/지급완료 URL은 검색 문맥을 유지해 새 지급 탭으로 연결한다. 미연결 과거 지급 기록은 별도 목록에 보존하며 현재 지급 가능액으로 사용하지 않는다. 개인 경비 월별 정산은 기존 기능을 유지하고 전사 월 점검과 구별했다. 수납 원장 미연결은 count=null, 환급은 실제 검토 거래의 입금·출금을 분리해 보여준다. 결의/개인/신탁 증빙은 조직·권한을 다시 확인한 다운로드 경로를 제공한다.

검증: 메뉴·업무현황·검토·회계 연결·이전 URL·지급 화면 등 12개 파일 86개 테스트 통과. 선지급 및 공통 지출 최종 4개 파일 30개 테스트도 통과. 최종 프로덕션 빌드와 변경 파일 ESLint 통과. 전체 TypeScript 검사는 기존 14개 오류가 남아 있어 통과로 표시하지 않으며 신규 파일 오류는 없다. 최종 격리 SQL 11개 묶음과 실제 여러 DB 세션의 지급·신탁·회계·선지급 중복/동시 처리 검증 통과. 실제 브라우저 카드·검색·Enter/Space·새로고침·15개 메뉴 순서·이전 URL 전환·미연결 과거 지급완료·증빙 다운로드·월 점검 결과는 local-integration-verification.md를 따른다.

남은 구현은 단순 운영 승인 대기가 아니다. 공통 화면의 완전한 원본 작성/결재 통합, 기존 표시이름 기반 승인 경로의 Auth UUID·조직 연결, 수납/환급 고유 ID 원장 연결, 선지급 확정·회계 확정/정정·전사 잠금이 남아 있다. 회계 확정 권한과 원본 수납 시스템은 사용자 답변 대기이며 해당 실행은 잠금 상태다. 운영 마이그레이션/배포 검증도 아직 하지 않았다.

## 4c 구현: 작성 진입·원본 상세와 서버 저장 결과 보존

`expense-entry-design.md`에 구현 전 원본·상태·금액·URL 대응과 검증 범위를 기록했다. 공통 지출관리에서 사전/사후 작성기로 바로 이동하고 결의 원본 ID 상세를 연다. 서버 빈 목록이나 저장 실패를 브라우저 과거 자료 또는 로컬 성공으로 대체하지 않는다. 저장 중 반복 요청을 막고 실패 시 입력을 유지한다.

관련 UI/route 54개 테스트와 프로덕션 빌드 통과. ESLint 오류 없음(기존 경고 1개). 전체 TypeScript는 기존 테스트 오류 13건이 남으며 통과로 표시하지 않는다. 이번 저장·재조회 검증은 서버 응답 대역을 사용하는 UI 회귀이며 실제 DB 역할/동시성 재검증이나 브라우저 검증 완료를 의미하지 않는다. DB 및 운영 자료는 변경하지 않았다. 서버 Auth UUID·조직·기존 결재선 권한 통합, 회계/정산 확정, 수납 원장 연결과 운영 적용은 미완료다.

## 4d 구현: 기존 지출결의 로그인 계정 연결과 원자 처리

`legacy-authorization-design.md`에 원본 관계·상태 전환·금액 계산·기존 URL 대응과 재사용/신규/정책 확인 구분을 기록했다. 기존 결의 목록·작성기·결재함은 검증된 Auth 사용자와 조직으로 조회한다. 작성자와 현재 결재 단계는 표시 이름 대신 UUID로 확인한다. 기존 문서 이름을 자동 매칭하지 않으며, 관리자가 `/finance/expense-authorizations`에서 원본과 계정을 선택하고 미리보기 후 명시 연결한다. 신규 초안 작성자만 현재 계정으로 자동 기록한다.

초안 헤더·항목·계정배분·증빙 연결·은행/카드 상태·감사, 승인 전환과 사실확인 초안 revision은 각각 하나의 DB 명령으로 저장한다. 원본 snapshot 및 연결 version이 달라지면 거절하고, 같은 처리키 재시도는 같은 결과를 반환한다. 승인대기 수정은 작성중으로 돌아가 결재 단계를 초기화하며 기존 이력은 유지한다. 일반 수정으로 지급일·정산완료·전표 결과를 생성하거나 변경할 수 없다. 첨부된 증빙 파일의 물리 삭제는 실행하지 않는다.

실화면 검증 중 사전 일반지출에도 실제 지출일을 요구하던 기존 검증 오류를 수정했다. 사전 일반지출은 실제 지출일을 비워둘 수 있고 집행예정일을 사용한다. 사후·개인 선지출·통장 선출금의 실제 지출일 요구는 유지한다. 예정일을 실제 지급일로 복사하지 않는다.

최종 자동 검증: 관련 UI·서버·권한·저장소 14개 파일 86개 테스트, 프로덕션 빌드, 격리 PostgreSQL 전체 12개 SQL suite 및 실제 동시 처리 검증 통과. 변경 TypeScript 파일 ESLint 오류 0개(기존 미사용 변수 경고 1개). 전체 `tsc --noEmit`는 기존 테스트의 13개 타입 오류 때문에 실패하며 신규 오류는 없다. 실제 Auth 브라우저와 원본 보존 검증 결과는 `local-integration-verification.md`에 별도로 기록한다.

운영 적용은 별도 단계다. 이 migration을 운영에 적용하지 않았고 기존 운영 계정 연결·승인·지급·서명도 실행하지 않았다. 회계 확정/정정 권한, 선지급 정산 확정, 수납 원장 선택, 사실확인 서명 정책은 미확정이므로 해당 실행 제한을 유지한다. 전체 원본 작성기 통합, 별도 기안 모듈의 기존 승인 경로 정비, 운영 배포 및 기존 자료 연결 검증도 남아 있다. 기존 지급 경로 전체와 보완자료 업로드의 Storage/DB 간 원자성을 이번 단계에서 새로 보장한 것은 아니다.

## 운영 적용 준비 1·2단계: 읽기 조사와 계정 연결 확인표

`operational-release-preparation.md`에 2026-09-08 운영 조사와 적용/복구 계획을 기록했다. GitHub에는 제품 커밋 `2f16168`의 Production 성공이 기록됐지만, DB 최신 이력은 `20260906135650`이며 신규 기반이 없다. 신규 후보 11개 외에도 이름이 같고 버전이 다른 과거 이력 22개가 있어 일괄 재실행하지 않는다. Vercel 직접 팀 조회는 403이고 운영 비로그인 GET은 로그인 화면까지 확인했다.

오프라인 스크립트로 실제 결의 6건의 계정 확인표 24행과 승인완료 기안의 역사 확인표 8행을 생성했다. 현재 활성 ADMIN 계정 1명과 문서상의 3명 간 관계는 확인 대기이며 UUID 선택 칸은 전부 비워뒀다. 실제 이름·UUID가 있는 파일은 ignored 로컬 경로에만 보관했다. 24/8행, 미지정 UUID, 신규 후보 11개, 공개 경로 출력 거절과 Node 구문 검사를 확인했다. 운영 증빙 4개 899,566바이트는 기존 ID 집합·크기·SHA-256과 일치했다.

운영 migration/계정 변경은 미실행. 실제 백업·복구 성공, 운영 schema와 과거 이력의 정의 동등성, Vercel alias 상세 및 런타임, 기안 모듈 UUID 승인 정비는 남아 있다. 제품 코드를 변경하지 않아 기존 빌드/SQL suite를 반복 실행하지 않았다.

## 4e 구현: 별도 기안의 UUID 승인과 이력 비교

`approval-authorization-design.md`에 원본·상태·금액·URL 대응과 재사용/신규/정책 항목을 정리했다. 기안 목록과 작성·상세·첨부 경로는 실제 Auth 사용자와 조직을 확인한다. 신규 기안은 현재 계정의 초안으로 저장하고, 관리자가 `/approval/authorizations`에서 단계별 계정을 명시 선택한 후 기안자가 상신한다. 현재 UUID 결재자만 승인·반려할 수 있으며, 이름이 같은 다른 계정은 허용하지 않는다. 업무현황의 내 결재도 같은 연결을 조회한다.

문서·항목·결재선·계약조건·의결 권고의 생성과 기안 상태 변경을 버전·처리키 기반 DB 명령으로 처리한다. 같은 요청 재시도는 원래 결과를 반환하고 동시에 다른 승인 요청이 들어오면 하나만 반영한다. 과거 승인 서명은 유지하고 새로운 감사에 Auth UUID와 연결/단계 snapshot을 기록한다. 기존 이름 기반 원본 변경 RPC를 폐쇄하고, 별도 계약/의결/지출 연결 서버 경로에는 조직 및 관리자 검사를 추가했다. 신규 저장과 수정 실패의 입력 보존도 정비했다.

과거 이력 22개의 실제 비교는 `migration-definition-comparison.md`에서 완료했다. 19개는 SQL 토큰 동일, 3개는 이력 구성 차이가 있으며 최종 객체 대응을 확인했다. 별도로 운영에 누락된 계정과목/은행거래 컬럼 15개 등의 실제 schema 차이를 확인했다. 신규 업무현황의 match_status 의존성이 있어 호환 변경과 운영 기준 리허설을 먼저 해야 한다.

운영 DB migration 12개와 실제 담당자 계정 연결은 미실행이다. 회계 확정/정정, 선지급 정산 확정, 수납 원장 연결, 사실확인 서명 정책은 미확정 실행 제한을 유지한다. 기존 소액경비 일괄처리 전체의 원자성, Storage/DB를 아우르는 첨부 원자성, 모든 원본 작성기의 공통 화면 내 통합을 이번 단계에서 완료한 것으로 보지 않는다. 검증 결과는 아래와 실제 브라우저 검증 문서를 따른다.

자동 검증: 기안·권한·기존 결의 route·업무현황 저장소 관련 12개 파일 39개 테스트와 최종 프로덕션 빌드 통과. 수정 TypeScript 파일 ESLint 오류/경고 0개. 전체 TypeScript 검사는 기존 금융 테스트 오류 13개 때문에 실패하며, 신규 기안 오류는 없다. SQL 전체 13개 suite 및 실제 여러 세션의 승인·지급·신탁·회계·정산 중복/동시 처리 검증과 후속 기안 focused 회귀 결과는 SQL 검증 기록을 따른다. 실제 Auth 브라우저 및 과거 첨부 보존 결과는 `local-integration-verification.md`에 기록한다.

## 운영 호환 변경과 격리 복원 리허설

`operational-compatibility-plan.md`에 운영에서 누락된 15개 컬럼, CHECK 6개, FK 2개와 인덱스 2개의 호환 계약을 기록했다. 과거 계정과목·은행거래의 의미를 임의 분류하지 않도록 subject_type/normal_balance/source/transaction_kind는 nullable로 추가하며 기존 값은 수정하지 않는다. 앱도 null을 미확정으로 유지하고, 모호한 입출금 거래를 출금 결의에 연결하지 않는다.

운영 읽기 전용 preflight에서 은행거래·계정과목·전표 0건, 결의 6건/32,120,120원, 검사한 제약 위반 0건을 확인했다. 격리 DB에서는 수집한 운영 catalog 범위의 구조 차이 0건을 확인한 뒤 가짜 자료 dump/복원, 별도 첨부 사본, 호환 SQL 선행 적용, 신규 12개 migration, 호환 SQL 재실행과 금융 SQL 회귀 10개를 통과했다. 기존 컬럼 원본과 첨부 지문은 유지됐다.

자동 검증: nullable 계정과목·은행 방향·화면 및 서버 출금 연결 관련 7개 파일 44개 테스트, 호환 SQL의 타입/제약/FK/인덱스 불일치 원자 실패·3회 재실행·기본값 보존 검증, 프로덕션 빌드와 변경 TypeScript ESLint를 통과했다. 전체 TypeScript 검사는 기존 금융 테스트 오류 13개가 남아 있어 통과로 표시하지 않는다.

실제 운영 PostgreSQL 접속정보가 없어 운영 DB 자료의 전체 백업·복원과 복구시간 측정은 아직 하지 않았다. 운영 DB migration과 실제 담당자 연결도 미실행이다. 격리 가짜 DB 자료 리허설을 실제 운영 DB 복원 성공으로 보지 않는다.

후속으로 운영 Storage 3개 버킷을 읽기 전용 백업했다. 실제 객체 34개/8,150,705바이트는 DB metadata 집계와 일치하고, 개별 백업 파일의 크기·SHA-256을 검증했다. 별도 로컬 Storage의 실행 전용 버킷에 전부 복원해 재다운로드 해시를 확인한 뒤 임시 버킷을 정리했다. 운영 Storage 쓰기는 없었다. 운영 PostgreSQL 직접 접속정보가 없어 DB 전체 dump/격리 복원과 복구시간 측정은 여전히 미완료다.
