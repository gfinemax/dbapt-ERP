# 담당자 선지급 정산: 다음 구현 단위 설계

2026-09-08 현재 코드 읽기 조사 결과다. 이 문서는 신규 구현 제안이며 정산 기능 구현·정책 확정·운영 적용 완료를 의미하지 않는다. 계약상 운영비 선교부와 담당자에게 지급하는 선지급은 서로 다른 거래다.

## 먼저 만들 안전한 단위

**실제 선지급 조회 + 원본 연결 정산 초안 저장·재조회**를 먼저 완료한다. 초안은 예산 USED, 회계 확정, 지급, 반납, 기존 결의 정산상태를 변경하지 않는다. 기존 대납 화면과 동일 증빙을 복사하여 새 비용으로 만들지 않는다.

연결 구조 제안:

`기존 EMPLOYEE_ADVANCE 결의 → workflow 거래 → 유효 DISBURSEMENT 배분 → 정산 초안 → 사용내역·증빙 ID`

`실제 RETURN 배분 → 동일 원지급 배분 → 정산 자금 합계`

`추가 지급 승인 대상 → 실제 DISBURSEMENT 배분 → 정산 추가 자금 합계`

- 정산에는 조직, 원결의 ID, 원 workflow 거래 ID, 작성자 ID, 버전, 상태, 메모, 원본 서명, 생성·수정시각을 저장한다. 이름은 표시용이다.
- 선지급 배분 연결은 고유 ID와 배분금액을 저장한다. 한 배분이 여러 회차 정산에 사용될 수 있는지는 미확정이므로 임의 부분 배정을 실행하지 않는다. 같은 원금이 둘 이상의 활성 정산에 전액 귀속되지 않게 DB 제약/트랜잭션 검사한다.
- 사용내역은 사용일, 금액, 원본 사용내역 ID가 있다면 그 ID, 증빙 ID, 계정·예산 검토 상태를 보존한다. 원금과 달리 실제 비용의 근거다. 증빙을 참조하며 원 파일·메타데이터는 삭제하지 않는다.
- 반환금은 기존 RETURN allocation ID를 참조한다. 이미 원지급 순액에서 차감한 반환을 정산 계산에서 다시 차감하지 않도록 **최초 지급 합계와 반환 합계를 분리**한다.
- 추가 지급은 기존 원금에 다시 더해 양쪽 계산에 포함하지 않는다. 최초 지급/추가 지급 분류와 각각의 배분 ID는 명시적으로 구분한다. 신규 추가 지급 승인 객체와 신탁 재요청 기준은 별도 정책 확인 후 연결한다.
- 과거 실제 지급액만 있고 신규 allocation 연결이 없는 원본은 원장 대조가 필요하다. 기존 actual_paid_amount와 신규 배분을 무조건 합치지 않는다. 실제 지급일·금액이 없는 과거 기록은 null로 두고 완료를 제한한다.

## 제안 상태 전환과 실행 제한

| 전환 | 조건 | 현재 정책 미확정 시 |
|---|---|---|
| 없음 → DRAFT | 조회 가능한 조직 원본, 원본 서명, 고유 처리키 | 구현 가능 |
| DRAFT → DRAFT | 버전 일치, 입력 보존, 증빙 조직 일치 | 구현 가능 |
| DRAFT → REVIEW | 사용내역·증빙·원금 연결 검증 | 승인자·권한 확정 전에는 초안 검토 표시까지만 |
| REVIEW → APPROVED | 실제 사용액과 예산 귀속의 승인 정책 충족 | 실행 제한 |
| APPROVED → RETURN_DUE / ADDITIONAL_PAYMENT_DUE / READY | 실제 유효 배분과 승인 사용액으로 계산 | 승인 정책 확정 후. 조회용 예상 차액은 별도 표시 가능 |
| READY → COMPLETED | 유효 실제 자금 균형, 승인 사용내역, 증빙, 중복 사용 없음, 최신 원본 | 실행 제한 |
| 완료 후 정정 | 사유·이력·역분개·월 마감 통제, 원본 삭제 금지 | 정정 정책 확인 후 |

상태명은 새 정규화 모델 제안이다. 기존 한글 settlementStatus를 덮어쓰거나 상태명만으로 과거 자료를 이관하지 않는다.

## 금액 계산 예제

`잔액 = 최초 실제 선지급 + 실제 추가 지급 - 실제 반납 - 승인된 사용액`

| 최초 선지급 | 승인 사용액 | 실제 반납 | 실제 추가 지급 | 현재 결과 |
|---:|---:|---:|---:|---|
| 1,000 | 800 | 0 | 0 | 200 반납 필요. 반납 예정 입력만으로 완료 불가 |
| 1,000 | 800 | 200 | 0 | 자금 차액 0. 증빙/승인 요건 충족 후 완료 |
| 1,000 | 1,200 | 0 | 0 | 200 추가 지급 필요. 사용비용 1,200 전체를 다시 지급하지 않음 |
| 1,000 | 1,200 | 200 | 0 | 이미 반환한 금액을 반영하면 400 추가 지급 필요 |
| 1,000 | 1,200 | 200 | 400 | 자금 차액 0. 지급원장 OUT 1,400 / IN 200, 사용비용 1,200 |
| 미확인 | 800 | 0 | 0 | 계산 확정 불가. 원결의 승인금액으로 대체하지 않음 |

3월 사용·6월 정산이라면 실제 사용일은 3월, 실제 반납/추가 지급일은 6월을 보존한다. 예산 귀속월과 마감 예외는 별도 정책·변경 이력으로 처리한다.

## 예산·회계 중복 방지 후속 단위

1. 선지급 원금은 자금 이동, 승인 사용액은 비용 판단 근거로 분리한다. 구체적 계정은 명시적 선택/검토를 유지한다.
2. 기존 예산에 원금이 USED로 잡혀 있는지, 정산 결의 사용액이 다시 들어왔는지 원본 ID 기준으로 대조한다. 합계가 같은 영수증을 이름·날짜만으로 자동 병합하지 않는다.
3. 예산 사용비용을 정산 사용내역으로 대체할 경우 원금의 기존 실적과 예약 해소를 원자적으로 조정하고 변경 전후 월별 원장을 남긴다. 기존 마감 자료를 조용히 다시 집계하지 않는다.
4. 선지급 승인에서 언제 예산을 예약하고 사용액 승인에서 언제 USED로 전환하는지, 미사용분 예약 해제 시점, 추가 사용의 한도 승인 정책은 확인 필요다. 정책 확정 전 예산 자동 전환 금지.
5. 현재 회계 연결 초안은 별도 승인·확정 실적을 만들지 않는다. 선지급/사용비용/반납/추가지급 각각의 원본 목적별 유일성과 계정 검토를 유지한다. 자동 비용 계정 선택을 도입하지 않는다.

## 완료 기준과 정책 질문

초안 단위 검증: 저장 후 새로고침으로 원결의·배분·사용내역·증빙 연결 재현, 조직 격리, 실제 작성자, 권한 밖 수정 차단, 동일 처리키 재시도 한 건, 동시 수정 한 쪽 충돌, 사용 중 증빙 삭제 방지, 원본 변경 시 입력 보존 및 재검토, null 실제액 유지. 저장 전후 기존 결의·예산·지급·회계 행수/금액/첨부 참조가 바뀌지 않는지도 확인한다.

후속 완료 단위는 위 여섯 금액 예제와 반환 역분개, 추가 지급 취소, 복수 정산 중복 원금, 동일 영수증 중복 사용, 월 마감 충돌까지 DB와 UI에서 검증한다.

확인할 정책: 담당자 선지급과 신탁 운영비 선교부의 승인 주체, 한 원금의 분할·회차 정산 허용, 추가 지급 별도 결의·신탁 승인 필요 조건, 사용액 승인/증빙 누락 예외 권한, 예산 예약/USED 전환 시점, 완료·정정 권한. 정책별 의존 실행만 제한하고 조회·초안·증빙 연결·검증은 계속할 수 있다.
